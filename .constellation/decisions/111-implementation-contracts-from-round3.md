# 111 第三輪盲點審衍生的實作契約（非使用者拍板，為實作者自行決定）

> ⚠ 本筆與其他決議性質不同：以下各項**未經使用者拍板**，是實作者依專案既有原則推導的技術契約。
> 記錄於此是為了不遺失，並讓拆票時能直接轉為驗收條件。若日後發現任一項其實含使用者可感知的取捨，應改為正式提問。

- **PID 重用防護**：關閉確認清單查出後到使用者按下確認之間可能間隔數秒，期間 Windows 可能將 PID 回收給無關程序。按下確認後**重查一次** console 清單，只終止「兩次查詢都存在」的 PID。依據：查詢實測僅約 200 ms，重查成本可忽略；此法既不誤殺新出現的程序，也不會終止已消失 PID 的新主人。
- **查詢失敗不得偽裝成無殘留**：`AttachConsole` 失敗、fork 失敗、逾時三種情況都不得收斂成「清單為空」。依據：專案既有原則（`MAP.md` 已知地雷段、決議 098／103 的揭露立場）。失敗時應照實告知無法確認，不顯示假綠燈。
- **「取消」的語意維持現況**：移除工作區路徑上按取消＝整個移除動作放棄（現行 `WorkspaceRail.tsx:279` 的 `confirmCloseWorkspace` 回 false 即 return）。不改變既有行為，避免新增使用者需重新學習的差異。
- **SCM 完整清理是第四條會關閉終端機的路徑**：該路徑（`LocalCleanupExecutor` → `teardownOnly` → `killWorkspace`）照樣執行殘留清理，但**不另跳確認**——使用者已在清理流程自身的風險確認中同意。另 console 查詢失敗不得使 `teardownStrict` 失敗而中斷既有清理流程。
- **WSL 列項於確認清單中加註記**：決議 103 將 WSL 限制寫入使用說明，前提是「WSL 分頁不會跳窗」；但移除工作區與關閉 Polydesk 兩條路徑會因存活終端機而跳窗並列出 WSL 終端機。該列項須附一行說明「此終端機內部的程式無法列出或清理」，避免空白殘留區被誤讀為「底下是乾淨的」。此為清單內的一行文字，非額外彈窗，與 103 的顧慮不衝突。
- **AI 狀態徽章跟著分頁搬移**：現行 AI session 依 cwd 前綴歸戶工作區（`claudeHookState.ts` 的 `matchWorkspace`），而存活判定依 `pidsOf(wsId)`；分頁搬移後兩者分屬不同工作區，會導致徽章與待確認通知在來源與目標**雙雙消失**。歸戶改以 termId／pid 為準，使徽章隨分頁移動。此為回歸防護，須進驗收清單。
- **排除查詢代理自身**：`GetConsoleProcessList` 的實作會先 `AttachConsole` 再列舉，故執行查詢的 fork 子程序必然出現在回傳清單中（實測建立期快照 `[4912,17652,2120]` 中的 4912 即為代理自身）。須排除，否則會列出幽靈項目，且該 PID 於代理結束後可能被回收。
- **導覽與使用說明納入完成定義**：本輪新增「分頁可搬到其他工作區」入口與「關閉時列出並清理底下程序」兩項使用者可見行為，依專案 `CLAUDE.md` 的同步規則須一併更新 `components/Help/`。
- **既有 e2e 斷言須同批更新**：決議 101 變更按鈕文案後，`e2e/terminal.spec.ts:31`（「仍要關閉」）、`e2e/app-close.spec.ts:115/167`（「全部關閉並退出」）等既有斷言會失效，須同批修正。
