# 105 殘留清單的程序名稱取自背景快取，與「殺誰」的判定分離

- 背景：ConPTY 的 `getConsoleProcessList` 僅回傳 PID 陣列，不含程序名或指令列。獨立審查據此認為確認清單將面臨兩難——顯示裸 PID 使用者無從判斷，或在關閉當下查詢名稱而付回決議 090 已被否決的數秒延遲。
- 決定：把「殺誰」與「叫什麼名字」拆成兩條路。**殺誰**：關閉當下即時查 console process list，準確且不受父子鏈斷裂影響。**名稱**：取自背景掃描順手維護的 PID→名稱對照表，關閉時直接查表、零延遲；表中查無該 PID 時顯示為未知程序並附 PID。另需將 `aiProcessScan` 統一走全列舉路徑（放棄 wmic 快路徑），使有 wmic 的機器也能取得完整對照表，並在該類機器重新量測負擔。
- 原因：本機實測顯示成本大頭在「啟動查詢程序」本身（單次 PowerShell 啟動即 1,285–1,974 ms），而非查詢內容——因此任何「關閉當下才查」的做法都會卡住使用者，逐 PID 查詢亦然。改由背景快取供名稱後，名稱過期僅影響顯示文字（最壞顯示舊名或未知），完全不影響終止對象的正確性；而決議 090 的實測已證實同一次背景掃描多帶資料為零額外成本。審查所述的兩難因此不成立。
- 證據：本機量測——PowerShell 啟動 1,285／1,431／1,274 ms（空查詢）、1,974／2,052／1,880 ms（Get-Process 版）；同程序內 WMI 逐 PID 查 5 筆 922–1,554 ms；全機列舉 2,064–3,075 ms。另 `aiProcessScan.ts:135-142` 讀碼確認 wmic 三查全數成功即 return，不進入全列舉分支。

> **superseded by 108**：名稱改為關閉當下以 tasklist 即時查詢（實測全列舉僅 0.5 秒），不再需要背景名稱快取與 aiProcessScan 全列舉改造。「殺誰＝即時查 console 清單」的核心分工不變。
